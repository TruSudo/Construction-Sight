The objective is:

**ONE COORDINATED INTELLIGENCE ENGINE → ONE SHARED INVESTIGATION STATE → MULTIPLE SYNCHRONIZED COMMAND CENTER VIEWS.**

Every source, investigative service, and assurance mechanism must contribute appropriately to this common operating system.

# VI. SHARED SITE INVESTIGATION — THE PRIMARY DATA PRODUCT

**The primary product of the intelligence engine is a continuously maintained, evidence-backed site/project investigation—not a raw source record.**

Each investigation must assemble the most defensible available account of the subject.

The investigation should contain, where available:

- Site and project identities
- Related source records
- Parcel and location evidence
- Owners, developers, contractors, and other parties
- Source-backed descriptions
- Relevant environmental review
- Permits and approvals
- Construction lifecycle observations
- Dated milestones
- Inspection evidence
- Conflicting claims
- Missing evidence
- Possible and confirmed relationships
- Provenance and verification status
- Historical revisions
- Recommended next verification actions
- Operational relevance and readiness assessments

Separate:

**Evidence certainty, identity confidence, investigation completeness, construction activity, and commercial readiness.**

These are different dimensions and must not be collapsed into one score.

For example, SMARTS regulatory status does not establish that construction is currently underway.

A CEQA approval is not an issued building permit.

A permit issuance does not establish that construction has started.

Satellite imagery must not be represented as current construction evidence without appropriate acquisition timing, interpretation, and independent corroboration.

Present what the evidence supports, expose uncertainty, and never manufacture missing facts.

# X. LIVE RELATIONSHIP GRAPH — DIRECT VIEW OF THE ENGINE

**MANDATORY FEATURE: The Relationship Graph must be an interactive, real-time visualization of the unified intelligence system's actual investigative state and processing activity.**

It is not a separate investigation engine.

It is not an independent source of information.

It is not a decorative visualization.

**THE ENGINE PERFORMS THE INVESTIGATION. THE GRAPH REVEALS ITS WORK.**

## A. Fundamental architecture

The unified engine must maintain authoritative, durable investigation state and an auditable history of material events.

The Relationship Graph must read directly from that shared infrastructure.

When background processing creates or changes a supported relationship, the graph should reflect the committed change.

Opening the graph must not be required for background investigation to occur.

The graph must reconstruct already completed work when opened later.

## B. Live visualization

Use the visual exploration style of VirusTotal Graph and an Obsidian vault network, adapted to ConstructionSight's approved industrial aesthetic.

The graph should organically display:

- Construction sites
- Projects
- Parcels
- SMARTS observations
- CEQA documents
- Permits
- Planning cases
- Government source records
- Developers and owners
- Contractors and subcontractors
- Consultants
- Contacts
- Inspections and milestones
- Evidence artifacts
- Identity candidates
- Contradictions and investigative gaps

Every node and edge must correspond to a retained entity, observation, candidate, or reviewed relationship.

## C. Live investigative events

Visualize actual recorded events such as:

- New source observation received
- Evidence retained
- Site investigation created
- Identity candidate generated
- CEQA filing correlated
- Permit or parcel relationship evaluated
- Entity relationship identified
- Contradiction detected
- Enrichment task started
- Enrichment completed
- Identity relationship validated
- Relationship rejected or superseded
- Investigation state updated
- Investigation requiring human review

Clearly distinguish:

1. **Committed knowledge:** Relationships and findings already recorded.
2. **Processing activity:** Work the engine is currently performing.
3. **Unresolved candidates:** Possible relationships that have not been established.

An animated connection must never falsely imply that an uncertain match has become verified.

Never create simulated investigation activity simply to make the graph appear alive.

## D. Real-time synchronization

Implement appropriate local event delivery, such as server-sent events or another justified mechanism.

Requirements:

- Snapshot of authoritative state on opening
- Live incremental updates
- Stable node and edge identities
- Durable revision identifiers
- Resumable event handling where appropriate
- Reconnection and missed-event recovery
- Idempotent graph updates
- No duplicate nodes from repeated events
- Consistency across application restart
- Clear connection and processing status
- Controlled memory and performance usage

The authoritative store—not the browser's temporary graph state—determines investigative reality.

Only committed information may update established graph relationships.

## E. User interaction

Implement:

- Zoom, pan, and drag
- Node expansion and collapse
- Force-directed or hybrid layout
- Search and focus
- Relationship-depth controls
- Entity and source filters
- Date and chronology filters
- Confidence and verification filters
- Evidence inspection
- Contradiction highlighting
- Clustering
- Saved investigation views
- Historical event replay
- Optional live-activity highlighting
- Reduced-motion and keyboard-accessible behavior
- Direct navigation to map locations and dossiers

Expanding a node should retrieve already indexed relationships.

It must not independently begin unrestricted investigations.

Additional research requests must enter the same authorized background task pipeline.

## F. Real-time versus historical operation

The graph must support two complementary experiences.

**Live mode:** The operator watches actual ongoing processing and committed investigative changes.

**Historical mode:** The operator inspects the accumulated network and can explore how relationships evolved through recorded events.

Closing or pausing the graph must not stop the investigation engine.

Reopening it must show everything persisted while it was closed.

## G. Single reality across all views

The Relationship Graph, Site Map, Project Intelligence, Evidence Chains, dossiers, and lead rankings must all derive from the same governed investigation state.

A relationship reviewed or rejected through an authorized workflow must be reflected consistently everywhere.

The graph does not maintain its own alternative identity-resolution decisions.

## H. Graph acceptance testing

Demonstrate that:

1. The background engine ingests an actual retained source observation.
2. Evidence is persisted with provenance.
3. A supported identity relationship or candidate is created.
4. The graph receives the committed event and updates.
5. Clicking a node exposes the corresponding evidence.
6. A related source observation updates the same investigation.
7. The graph updates without refresh.
8. Contradictory evidence is visibly distinguished.
9. Closing the graph does not interrupt background processing.
10. Reopening it reconstructs the authoritative current network.
11. The map and dossier agree with the graph.
12. No duplicate or invented findings appear.

**A visually animated demonstration is insufficient without proving actual backend integration.**
